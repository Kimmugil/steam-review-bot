# 스팀 리뷰 탈곡기 (steam-review-bot) v4

스팀 게임의 유저 리뷰를 **언어별로** 나눠 평가와 이유를 정리하는 웹 서비스입니다.
숫자는 코드가 스팀에서 받아 계산하고, AI는 무작위로 뽑은 리뷰 표본을 읽고 **해석만** 합니다.

## 한눈에 보는 구조

```
방문자 ─ 웹(Vercel, Next.js) ──요청──▶ DB(Supabase, thresher 구역)
                │                         ▲
                └─ GitHub Actions 깨우기 ──▶ 분석 실행기 ─ 스팀(숫자·리뷰·공지) ─ Gemini(해석) ─┘
```

- **웹**: 홈(요청·목록) · 리포트 · 분석 방법 · 관리자 · 화면 문구 관리
- **분석 실행기**: `scripts/run_analysis.ts` — GitHub Actions(`analyze-report.yml`)가 분석 ID 하나를 받아 실행
- **DB**: Supabase 프로젝트 안의 `thresher` 구역(전용 계정 `thresher_app`). 구조는 `db/schema.sql`

## 분석 원칙

1. **숫자는 코드가** — 스팀이 알려 주는 "조건에 맞는 긍정/부정 건수"를 그대로 가져옵니다(전체·기간별·언어별·플레이타임별). 95% 신뢰 구간과 "우연일 수 있는 변화" 판정을 함께 계산합니다.
2. **기준은 게임마다** — 분석 기간(리뷰량), 플레이타임 구간(그 게임 리뷰어 분포의 사분위), 변화 판정(그 게임이 평소 흔들리는 폭)을 모두 그 게임 자신의 데이터로 정합니다. 고정 숫자 기준을 쓰지 않습니다. 직전 기간이 평소와 달랐으면(리뷰가 몰린 때) 변화 해석을 막고 알립니다.
3. **표본은 치우치지 않게** — 분석 기간을 5구간으로 나눠 무작위로 뽑고, 언어 안에서 긍정/부정을 실제 비율대로 뽑습니다(도움순은 비판적인 글에 치우쳐 쓰지 않음).
4. **AI는 해석만** — 주제를 찾고 근거 리뷰 **번호**만 가리킵니다. 번호 검증, 주제 비중, 추천 비율은 코드가 계산하고 인용 원문은 DB의 실제 리뷰를 붙입니다. 원인 추측은 금지합니다.
5. **언어 기준** — 국가가 아니라 리뷰를 쓴 언어입니다. 모든 화면에 그렇게 표시합니다.
6. **실패를 숨기지 않기** — 수집이 실패하면 0으로 채우지 않고 실패와 이유를 보여 주며, 방문자의 오늘 한도 1칸은 돌려줍니다.

## 방문자 요청과 한도

- 누구나 요청할 수 있고, 같은 게임의 리포트가 있으면 "그 리포트 볼래요 / 새로 분석할래요"를 먼저 고르게 합니다. 같은 게임이 진행 중이면 그 분석으로 안내합니다(게임당 동시 1건).
- 방문자의 새 분석은 **하루 30회**(한국 시간 자정에 초기화). 관리자 화면에서 바로 바꿀 수 있습니다. 한도 확인과 접수는 DB 함수(`take_daily_slot`)로 한 번에 처리해 동시에 눌러도 넘지 않습니다.
- AI 호출은 월 상한(기본 300회)이 있어, 닿으면 숫자만 저장합니다.

## 개발

```bash
npm install
npm test           # 계산 로직 시험
npm run typecheck
npm run dev        # http://localhost:3000
npm run analyze -- --new <App ID>   # 내 컴퓨터에서 분석 한 건 실행 (.env.local 필요)
```

배포·환경변수·비밀값 설정은 [docs/DEPLOY.md](docs/DEPLOY.md)를 보세요.

## 예전 방식(v1~v3)

구글 시트에 저장하던 시절(2026-04~08)의 리포트 20건은 DB로 옮겨 "예전 방식" 표시와 함께 보관합니다.
숫자 기준(공식 평가 표기, 표본 방식)이 달라 새 리포트와 직접 비교하지 않습니다.
